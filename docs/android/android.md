# Android App

`android/`: the Android client, in Kotlin + Jetpack Compose. It connects to the same hub with the same API as iOS (`docs/protocol/protocol.md`); the server needs no changes.
minSdk 30 (Android 11), compileSdk 37, targetSdk 37. The UI comes in three languages, 简体中文, English and 日本語. It follows the system by default and can be chosen in Settings; see "Internationalization".

In one sentence: on an Android phone, see the Agents in the engine of each of your computers (herdr, Herdr App, Orca or Paseo, one per computer, `docs/integrations/engines.md`), send messages, answer questions / approve plans / grant permissions, and press the options of terminal dialogs,
without any push account.

## Aligning the Agents list and the Machines page (#3038)

- **Sorting**: the list settings have "Sort: **Status first** / **Recently updated**" (iOS `AgentSort`, stored on the device). With recently updated, sessions in each group sort only by time, and active spaces, repositories and computers sort by their newest session, first. With status first the sections stay the same; only the order inside a section is by time. The logic is in `AgentList.kt` in `core:domain` (`AgentListSettings.sort`).
- **Origin filters and the botmux toggle**: the quick filters gain **Lark groups / Terminal** (#2526: botmux sessions / herdr panes, decided by the `pane_id` prefix, `agentSource` in `SessionSource.kt`). As on iOS / web, filters only show items that have Agents, and a selected item that becomes empty stays. When there are too many items for one row (all six have Agents), the Brief labels and the Board count cells switch to horizontal scrolling (each Board cell is at least 92dp wide and still splits the width evenly when it fits; when scrolling, a sliver of the next cell shows at the edge) instead of squeezing into ellipses (screenshot `AgentsParityShotsTest.sixFilters`, 360dp wide). The **botmux** capsule under the filters (web #2786) hides / shows botmux sessions on this device. It appears when there are botmux sessions or they are hidden; the number is the botmux session count under the current scope, computer and search (when not hidden it reuses the **Lark groups** count; when hidden it counts separately, without building the list again). Hiding while on **Lark groups** goes back to **All**; choosing **Lark groups** while hidden shows them again.
- **Origin label on session rows** (#3132, same as iOS / web #2698, placement per #3043): botmux sessions are labeled **Lark group**, herdr panes **Terminal**; other hosts and Persona's own chats get no label. The label sits at the top right, under the time, right-aligned, at the time's font size; the title starts at the line start and is not squeezed. The compact list has only one line, so the label goes before the time. When a Lark group has an https `external_url`, tapping the label opens that thread (through the shell's link handling, inside the App). Colors come from the design system's origin colors (`PersonaPalette.sourceFeishu` / `sourceTerminal`, same as iOS `Theme.sourceFeishu` / `sourceTerminal`; Brief uses ink only). Screenshot `AgentsSourceShotsTest`.
- **Three kinds of empty state** (iOS `ChatsView`): no search results is "Nothing found for “xx”", without **New session**; no sessions at all is "**Start your first coding session** / **No sessions on this computer**" + **New session**; an empty quick filter is "No XX sessions" + **Show all**.
- **Why herdr didn't start**: under the "herdr isn't running on this computer" card, a red line "Didn't start: reason" stays (known node errors turned into plain words, same as iOS `HerdrFailure.says`) until the next start or until herdr is read as running; long-press copies the hub's original text and the HTTP status.
- **Subscription usage**: the top of the machine monitoring page (overview) lists every account from `GET /api/v1/usage/windows` (of every paired hub group, see "Multiple hubs"), fullest first, expired last: a usage bar per window (turns the warning color from 80%), the reset countdown, the sample time, whether usage is running fast / slow, and a mark when the gateway can't be read. When the hub has no data (or an old hub lacks this endpoint) the whole section is hidden; while the page is in the foreground it reads once a minute. The logic is in `UsageWindows.kt` in `feature:machines`, with the same rules as the web's `lib/usage-windows.ts`.
- **What this computer can do**: after the computer card and the engine, the machine page reads the node self-check (`GET /machines/{id}/doctor`) and shows each feature as **Ready** / **Partly working** / **Broken** / **Off**, with **Check again**; when files Persona generated are stale or missing there is **Fix** (after confirming, `POST …/doctor/fix`); "See all checks" expands every item. Node too old, hub too old, offline and insufficient device permission each get one sentence; when the node is too old and can be redeployed there is **Redeploy**. The logic is in `NodeHealth.kt`, with the same rules as the web's `lib/node-health.ts`.
- **Browser (ego lite)**: when the hub's ego plugin is on (the machine has `browser`), a Mac's machine page has the **Let the assistant use this browser** toggle, install / uninstall, the first-time setup steps (open ego lite, import data from other browsers, finish setup, check again) and, once ready, its status (imports, usage stats), same as iOS `BrowserSection`. While a task is running or first-time setup is in progress it reads every 2 seconds. The phone has no live view of that Mac (the iOS "VNC" button); first-time setup is done on the Mac.
- **Not done yet**: "Control computer" (Cua) and "Browser sign-in" (importing cookies) on the machine page, attachments in a new Agent's first message, "New worktree…".

## Notifications (no push service)

Android shares the hub WebSocket through the foreground service in `:platform:notify` and does not depend on FCM or vendor push. Notification channels, restore on boot, network reconnects, keep-alive scheduling and the setup checklist for Chinese-vendor ROMs are implemented.

Device record (2026-10-31, ColorOS 16 / Android 16, single observation): with the foreground service running, the WebSocket was still cut about 6 seconds after the App went to the background, and reconnected automatically when it came back to the foreground. In system settings the App needs "Allow background activity" and "Auto-launch" turned on and battery set to not optimized (the checklist's "Background keep-alive" item guides this). How long it stays connected in the background after that, and how much battery it uses, are to be measured per acceptance item V03; not measured yet.

- "Finished" is decided by the hub with the same completion policy as iOS and delivered as a `notify` event; the client receives it after declaring `ws_notify` and no longer infers completion itself.
- Questions, plans, permissions and screen options can be answered from the notification; allowing or approving requires unlocking, and denying or sending back can include a reason. Negative buttons go on the left and positive on the right (**Deny / Allow**, **Send back / Approve**), consistent with the ongoing notification and Android dialogs; questions and screen options keep their original order. When the result is unclear it says it's waiting for confirmation and never re-approves automatically. Permission cards requiring field values (required `fields`, such as a password when adding mail) have no App form yet. Cards, one-tap approval, request notifications and the ongoing notification offer no Allow, only Deny; the card says to handle it on the web or iPhone (`needsFieldValues`, #4987).
- Tapping a notification and session deep links go through the same navigation entry (the same on cold start and when the App is already open). When the notification link specifies `tab`, it lands on Persona or Agents directly, without waiting for session metadata; when it doesn't, it waits for the metadata to arrive before routing. The terminal fallback action (`target=terminal`) opens that session's terminal, and back returns to the original chat. Cards not attached to a session (empty `session_id`, e.g. `personad ask` in a plain terminal, #4515) still raise notifications; opening one lands on the Agents page: first any chat open on the Agents page is closed, then if the card is in the list it opens directly (the link carries `machine` and `request` but no `session`, used only locally on the phone, #4808). There is no terminal button.
- The setup checklist offers system entries for notification permission, battery restrictions, auto-launch and so on, plus scheduling, showing and reporting a lock-screen test. Lock-screen survival, notification display, recovery after reboot and battery use on each ROM are all unmeasured.

## Connection addresses (Settings › Connection diagnostics)

Requested 2026-11-01: "Current connection" and "Candidate addresses" must support adding and editing. The hub doesn't always publish all its addresses (for example, when a NAS's network card sits on a virtual switch, the hub treats it as a virtual interface, so its IPv6 and intranet https addresses are not sent out); in that case you add them on the phone by hand. The semantics match "manually add address" for computer links ([link.md](../operations/link.md)); the difference is that on Android these settings belong to the pairing.

Candidate addresses have three sources, each marked in the list:

- At pairing: `url` and `alt` in the pairing link, the https address built from `url` + `tls`, and `/api/v1/endpoints` read during pairing;
- From the hub: the authenticated `/api/v1/endpoints`, the WS `hello` and `endpoints` events ([protocol](../protocol/protocol.md#候选地址)). As soon as the hub's list arrives it replaces the pairing-time batch;
- Added manually: stored only on this phone; the hub's list never replaces them.

What you can do:

- Add: `https://domain:port`, `https://[IPv6]:port`, `https://IPv4:port`. Without a scheme it assumes https; the port is required; paths, `?`, `#` and user names are rejected; IPv6 needs square brackets. Validation does no DNS lookup and no networking (`checkEndpoint` in `core:hub`); errors are shown in Chinese under the input field, and when valid it previews the normalized form that will be saved (`scheme://host:port`, port always written out). Each pairing allows at most 10 manual addresses; duplicates of an existing candidate (compared by normalized form, so `https://host:port/` and `https://HOST:port` are the same) are rejected.
- Security rules are unchanged: https addresses are pinned to the public-key fingerprint from pairing, as at pairing time; when the pairing has no fingerprint (the hub has no TLS, or sits behind a reverse proxy), https addresses are checked against system-trusted certificates and the domain ([network.md](../operations/network.md#反向代理的子路径android)). `http://` must be on the local network: IP literals must pass `LocalAddressPolicy` (loopback, private, link-local, ULA), and names are only accepted as `localhost` and `.local`; at runtime `HubHttpClient` still checks again against the resolved peer address ([network.md](../operations/network.md)).
- Manual addresses can be edited (position and disabled flag stay) and deleted (with confirmation); pairing-time and hub-sent addresses can't be changed, only disabled and re-enabled; manual ones can be disabled too. At least one enabled address must remain. "In use" marks the one currently connected.
- Each one can be **tested**: a fresh connection pool with pinning requests `GET /api/v1/health`, checks hub_id, and shows the result and time taken. The time includes connection setup, and for https the TLS handshake; it is a single sample, labeled "single" in the UI, and is not a performance baseline. Results stay in memory only. Each row also shows the probe result from the connection's own route selection (labeled "auto-probe"); whichever is newer is shown.

**List order is the order they are tried** (requested 2026-11-02: "users must be able to drag candidate addresses; the display order is the trying priority"). However the list is ordered, the connection tries it in that order, with no hidden reordering: the old "prefer this" and "on reconnect, first try the one that last worked on the same network" are both gone.

- Reordering: drag by the handle on the left of a row, or long-press a row and drag; dragging to the top or bottom edge scrolls automatically. The row menu has "Move up" and "Move down", and accessibility services get actions with the same names. The number on the handle is this entry's position in the trying order (disabled ones are not numbered).
- Before any reordering, the default rules apply (`orderEndpoints`): public IPv6 → domain → local network → public IPv4 → other; within a kind, https before http; within that, manual before pairing-time / hub-sent; finally the original order (manual ones by when they were added, the rest in the hub's order).
- After reordering, the user's order wins (`arrangeEndpoints`): new addresses from the hub and newly added manual ones go to the end; addresses the hub no longer offers disappear from the list (an address whose IPv6 prefix changed counts as new and goes to the end). "Restore default order" (with confirmation) goes back to the default rules.
- Disabled addresses stay in place, grayed out and labeled "Disabled", and are skipped when connecting; they can still be dragged, and when re-enabled they're still where they were.

How connecting works: only enabled addresses are tried, starting strictly in list order. Each one starts after the previous one fails, or 1 second after the previous one started (`HubRouteSelector.STEP_MILLIS`), and whichever passes the identity check first wins; so a later entry can only win once the one before it has been tried alone for 1 second. Once connected, every 5 minutes (`OkHttpHubConnection.RECHECK_MILLIS`) it checks the addresses ranked above the current one, waiting at most 1 second each; if any answers, it reconnects (that round races everything and picks the first to answer). The connection never moves itself down the list. Dragging or restoring the default order only changes the order; it doesn't probe or switch right away: the connection follows the new order on the next reconnect or the next 5-minute recheck, and dragging doesn't drop the connection in use (decided by the user 2026-11-02); only disabling, deleting or editing the address in use reconnects directly. Both 1 second and 5 minutes are configured values, not measured.

Storage: manual addresses, disabled flags and the user's order are saved per pairing (`ScopedHubData.endpoints`, `endpoints.enc` in the pairing directory, encrypted with Tink AEAD like the credentials) and survive restarts; a new list from the hub doesn't change them; signing out, revoking and re-pairing delete them together with the pairing directory (`eraseScope`). If the file can't be read it is treated as "default order, no manual addresses" and does not block the whole pairing (if the credentials file can't be read, the original file is kept and an error is reported). A "prefer this" saved by the previous version is read back as an order where that entry is first and the rest follow the default rules.

Code: validation, normalized form, kinds and ordering are in `core/hub/.../HubEndpoints.kt`; racing is in `HubRouteSelector`, the recheck in `OkHttpHubConnection`; the settings page controller is `HubEndpointSettings` (implements `ConnectionEndpoints` from `core:contracts`) and is handed to Settings (`PairingModule`) by `ConnectionRuntime.endpoints`; storage is `core/data/.../EndpointOverridesStore.kt`; the page is `feature/settings/.../EndpointsSection.kt`, `EndpointEditorState.kt` and dragging `EndpointDrag.kt` (candidate rows use `JRow`'s slot style, so margins line up across all three styles). Demo mode has no such service, and connection diagnostics stays read-only there.

Screenshots: `MOCK_ENDPOINTS=1 python3 scripts/mock/mock_hub.py --tls-port 0` makes the mock hub also send two unreachable documentation addresses (`[2001:db8::10]` and `hub.example.com`), for looking at failed tests and disabling. Pairing with a fingerprint needs `persona://pair?url=…&token=mock&hub=<hub_id>&fp=<fp>&tls=<TLS port>`; read `hub_id` from the mock hub's `/api/v1/health`, and take `fp` and the port from the "TLS 端口=… fp=…" line ("TLS port=… fp=…") it prints at startup (`debug.mockAddress` only configures a plaintext address; without a fingerprint you can't add an https address).

## Composer (attachments, camera, dictation, "/" commands, @ mentions, quote cards, queue strip, refused messages)

Ported 2026-11-02 from the old App on the main line (inventory items C1–C4, D1, D7). The composer on the chat page and in Persona is the same `ChatComposer` from `feature/chat`, and the behavior below is the same in both (the queue strip is only in Agents chats).

- Photos and files: **+ › Photos** takes up to 4; each is uploaded to that computer as soon as it's picked (`POST /api/v1/machines/{mid}/files`), long edge scaled to 1600, JPEG quality 75 (same as iOS). Photos sit in a row of 64dp square thumbnails above the composer (design system `AttachmentThumb`, decoded in the background at thumbnail size), with an ✕ at the top right (**Remove this one**); uploaded ones have a pen at the bottom left, and a tap opens the markup editor (see "Viewing and marking up images"). While uploading they are dimmed with a spinner; on failure they get a red border and **Retry**, a tap re-uploads, and the reason is written in one line under the thumbnail; photos that can't be read, or that exist only on the computer after being restored by **Pull back to edit**, show a placeholder icon. Files are still one per row (name, state, retry, ✕). When picking a file it pre-checks `OpenableColumns.SIZE`; anything over 200 MB is marked invalid right away ("“name” is over 200 MB and can't be sent") and is neither copied nor uploaded; when the size can't be read it still counts while copying. With only photos and no text or files, the body sent is "Please look at the photos", and the photos are still written as an `<attached_images>` tag. When coming back from the camera or file picker the connection is often still catching up, so uploads first wait up to 15 seconds for `readyToSend` (`UPLOAD_READY_WAIT_MILLIS`, configured value, not measured), then report "retry upload once the connection is back". Offline, photos are not queued with the message (decided: not doing it).
- Camera: the App declares CAMERA for QR pairing, and Android then requires the permission before it can launch another camera App. **+ › Take photo** first checks the permission and asks with `RequestPermission` if missing; on denial (including "Don't ask again") it shows **Camera access needed**, explaining that it can be turned on in system Settings › Apps › {App name} › Permissions, and **Open settings** opens this App's system details page. With no camera App it says **No app on this phone can take photos**. The original capture is kept in `cache/chat-captures` (FileProvider `${applicationId}.chat.files`) and deleted only when it leaves its draft (removed with ✕, or the composer is cleared after sending): the composer watches its own draft's changes by attachment id and deletes from that; it never scans the directory (drafts of other sessions may still reference files in the same directory). Code: `ComposerCamera.kt`.
- Dictation: the microphone (**Dictation**) is always there, same as iOS `ShellComposerBar` (#2976 G058): with content, the send key is to its right, and after typing you can keep dictating to append; when the Agent is working and there's no content, the right side is **Stop**; with no content and not working there's only the microphone. Tapping it opens the phone's own voice input (`RecognizerIntent.ACTION_RECOGNIZE_SPEECH`, `LANGUAGE_MODEL_FREE_FORM`, `zh-CN`, prompt "Go ahead; what you say goes into the message box"); any vendor's recognizer works, no Google services needed, and the App doesn't record or need the microphone permission. Without a recognizer the button is hidden (the `feature/chat` manifest declares `<queries>`; on Android 11+ it can't be found without it); a launch failure says **No voice input on this phone**. The recognized text is appended to the end of the draft with the cursor at the end, not inserted at the selection (`withDictation`: first trims trailing whitespace from the draft; if the draft ends with an ASCII letter or digit and the first recognized character is also ASCII, a space goes in between; Chinese is joined directly). Code: `Dictation.kt`.
- "/" quick commands: the command table `SlashCommand` (the same set as iOS: continue `/继续`, `/compact`, `/context`, commit and push `/提交`, report progress `/汇报`; the English UI shows e.g. `/continue`) plus **Clear context /clear**. In the "+" sheet a tap sends right away. When the composer holds only one "/word" (starting with `/`, no spaces or newlines), commands matching the prefix (case-insensitive) are listed right above the field (design system `ComposerSuggestions`: the word in bold, the description on the right, /clear in the danger color); tapping one puts its text in the composer (not sent, cursor at the end), and the list closes when the draft is exactly the only match; tapping /clear clears the composer and asks for confirmation. /clear is only for Claude in a terminal-engine pane (positive check `canTypeClaudeCommands`: Claude, can send, has a terminal, has a pane, not Persona), and only appears when it's not working and not already clearing (both in the list and in "+"). The confirmation: "{Agent} will start a new session, and this chat stays in history; the page jumps to the new session once it appears. Anything you haven't sent on the phone is kept." **Clear** is the danger button. After sending it waits up to 20 seconds (`CLEAR_WAIT_MILLIS`) and opens another running session if one appears in the same pane; on timeout it says "Sent /clear. Open the new session from the list once it appears." and offers /clear again (no message if this /clear hasn't gone out yet or was refused; the bubble says so itself); a failed request stops waiting immediately.
- /model and /loop (#2976 G052, web `AGENT_COMMANDS`): they only appear in the "/" list, not in the "+" sheet (where a tap sends). /model is for Claude in a terminal pane (`canTypeClaudeCommands` and able to change mode); tapping it clears the composer and opens the **Mode** sheet (which has a **Model** section, see "Model" below). This is a one-shot request (`openRequested`, cleared by `onOpenHandled` after opening), so when a question card hides the composer and it comes back, the sheet doesn't pop open by itself; when the draft is exactly `/model` the list doesn't close either, and only a tap opens it. /loop is for the same sessions; tapping it puts `/loop ` in the composer. When the draft is a /loop command, a line above the composer says what it will do (`loopHint` in `ComposerLoop.kt`, same copy as the web: "Repeats every 10 minutes: …", "Repeats at Claude's pace: …"; with no task given, it shows the format in the warning color).
- @ mentioning a file or session (#2976 G043, iOS `PromptItems`, web `MentionMenu`): the @ button right of "+" types an `@` at the cursor (adding a space first if a character precedes it). When the text before the cursor is `@word` (at the start or after whitespace, so email addresses don't count), `ComposerSuggestions` lists right above the field: files that tools read or wrote in this chat (`file_path` / `notebook_path` of `tool_use`, newest first, at most 12), with the directory on the right (relative path for files in the session directory, "File this session used" for the root); tapping one replaces it with `@relative/path `. Then other sessions (excluding Persona chats and this session, by update time (parsed time, not string comparison: the hub's fractional seconds vary in length), at most 8), with "Agent · directory · as context" on the right; tapping one deletes the `@word` and puts that session as a context card above the composer (`persona://session/<machine>/<session>`, body "Another session: title (Agent) / directory / it last said: …"), sent with the next message as `<persona-context>`, as on web and iOS. ## Multiple hubs (connected to several groups of hubs at once)

#295; the design and the interface contracts between lanes are in [plan-hub-mesh.md](../archive/operations/plan-hub-mesh.md) sections 4 and 2.6; iOS is #256. The phone can pair with several hubs:
hubs that reach each other (linked hubs) form one **group**, which keeps a single connection and switches routes inside the group; different groups (environments that must stay apart, like work / personal) each have their own connection and don't affect each other.
Agents, machines and requests that need you are shown merged across groups; Persona, Inbox and hub-related settings belong to each group and use "the selected group".

### Grouping and group ids

- The group registry (`GroupsDocument`) records each group's id, name (as renamed by the user), storage scope, paired hubs (`hubs`; the first one is the group connection's own hub),
  hubs discovered through linking but not paired (`mesh`: address, fingerprint, name), plus `primary` (the primary group) and `selected` (the selected group). It is encrypted like the credentials (Tink AEAD); if it can't be read, the original file is kept and an error is reported.
- **Grouping**: the authenticated hello carries `mesh.hubs` (plan 2.6), all hubs in the connected component this hub belongs to. Each time one arrives it updates each hub's peers: hubs in the list become each other's peers, and hubs outside the list drop the list members they had listed (so a new hello can correct stale information other hubs left behind).
  Two paired hubs are in the same group as long as either one's peers include the other; a group is a connected component (`learn` / `regroup`, pure functions, `HubGroupRegistryTest`). Hubs without the `mesh` field (hubs from before L1 merged) only update their name and form a group of their own.
- **Group ids** are generated on the phone (`g` + 8 hex digits) and are stable: a merge keeps the oldest id (the side containing primary-group members gets the primary group's id first); on a split the side containing the original group's first hub keeps the id, and the side left without one gets a new id and a new empty scope.
- **Merging loses nothing** (required by the maintainer 2026-11-02): the merged-away group's data is not deleted at first; the registry records a `PendingMove` (its scope, and which group it merged into). Once it's closed and the merged group is open, its **unsent messages** (everything except shown and cancelled ones; one interrupted mid-send is recorded as "result unclear" and checked with the hub before deciding to resend) and **non-empty drafts** are moved into the merged group: messages keep their original `client_msg_id` (the hub deduplicates by it, so delivery semantics don't change), machine and session ids don't change (after linking, machine ids are stable within the group, plan 2.6), and a non-empty draft for the same session already in the merged group isn't overwritten. Only after the move is that scope deleted (its paired hubs keep their credentials); caches aren't moved but fetched again. If the move fails (e.g. the database can't be read) it stays and is retried on the next registry change or the next launch, never cleared silently; if it crashes halfway, moving again doesn't duplicate anything (messages dedupe by `client_msg_id`, drafts aren't overwritten). Groups the user disconnected and revoked groups are not moved (the disconnect confirmation says local data will be cleared). Code: `GroupMerge.kt`, `HubDataStore.unsentAt`, `ConnectionRuntime.moveUnsentLocked`.
- On a split (one group becomes two), the split-off group uses a new empty scope; messages still in the original group's pending queue that belong to computers of the split-off hub are not moved; sending them fails and is shown (they don't vanish silently).
- **Pairing a hub that's already in some group** (it's in some group's `mesh`, or some hub's peers include it) merges it into that group automatically, without showing it twice; pairing the same hub again only replaces its credentials, and the group and data stay.
- **Migration**: on the first launch of the new version, the old single pairing becomes the primary group in place: its storage and its only hub are both the original pairing directory, and no files move. Database tables were already split by pairing scope (the `scope` column), one directory per group, so **there is no Room schema migration**, and the version numbers of `ItemsDatabase` / `PersistentDatabase` are unchanged; the migration tests cover the registry (`HubGroupRegistryTest`, instrumented test `HubGroupsDataStoreTest`).

### Keys: the group suffix on machine ids

Android's take on plan section 4 ("session keys must tell groups apart"), decided by the maintainer 2026-11-02:

- For the **primary group** (the group migrated from the old single pairing, or the first group paired), machine ids, session keys, routes, deep links and notifications are byte-for-byte what they are now. **Every other group's** machine ids carry a stable `~<group id>` in the merged list (`GroupKeys`, e.g. `macbook~g0a1b2c3d`), so a session key becomes "group + machine + session". Only valid group ids are recognized as suffixes; the hub's own collision suffix `@<hub>` is part of the machine id and is kept as is.
- The suffix **does not follow the selected group**: switching the group used for Persona / Inbox changes no key, so open pages, the back stack, notification deep links, drafts, pins and caches never get crossed. When the primary group is disconnected, the other groups stay as they are and no new primary is promoted; once all are disconnected, the next group paired becomes the primary again.
- Interaction ids (things for you to decide) are chosen by each hub, and two hubs may use the same one (the fixtures of two mock hubs are identical, and the list once crashed outright on duplicate LazyColumn keys): interaction ids in non-primary groups carry the same suffix, stripped when answering; `interaction_resolved`, `interaction_id` in `notify`, and the interaction ids and the machine part of entry ids (`machine/session`) in fleet entries change together.
- Each group's own repositories, database and transport use only unsuffixed ids. The facades (`GroupNames`, `MergedServices.kt`, `GroupTranslation.kt`) add the suffix when passing data up to lists and strip it when handing calls to that group. This way the signatures of `Session` / `Interaction` / `SessionKey` / `ChatActions` don't change, and feature pages, routes, deep links and notifications barely need to change.
- Trade-off: unlike iOS, no field was added to `SessionKey`. That would require every place that builds a key from a route, deep link or notification to carry the group, and missing one would cross groups; the suffix encodes the group in the machine id, so it's never lost wherever it travels. The cost is that the facades translate interface by interface (lists, events, preference paths, draft keys, results of creating sessions…), and new interfaces carrying a machine id must be added to `GroupNames`.

### Connections and switching routes

- One `OkHttpHubConnection` per group. The first paired hub in the group is its own hub; the other paired hubs and hubs discovered through linking are `members`: their candidate addresses come after its own, all through the existing route selection rules (strict order, 1-second steps, the 5-minute recheck only moves forward, `HubRouteSelector`). When the connected hub drops, the next round of route selection lands on another hub in the group; when it recovers, the recheck moves the connection back.
- Each candidate is pinned to its own hub's fingerprint and its hub_id is checked; members' fingerprints come from the authenticated hello (trusted), and another hub's certificate in the group can't impersonate this one (checked by host:port during the handshake; OkHttp doesn't provide `handshake.peerCertificates` for self-signed certificates). Requests and the WebSocket use the credentials of the hub on the current route: paired hubs use their own, hubs discovered through linking borrow the group credentials (plan 2.6, "credentials are shared within a group").
- When a hub rejects its own credentials (401), only that hub is removed from the group (its pairing is deleted from the registry and the group reopened); the other hubs keep working; only when none are left is the group invalid. A hub that only rejects borrowed group credentials is just no longer tried, and nothing is deleted. When the last group becomes invalid, it's the same as with a single pairing before: all data is cleared and the state is "pairing invalid".
- Different groups have one connection each, and these are what the foreground service keeps open. Disconnecting a group closes only its connection and clears only its data; other groups aren't affected. The exception is the ungrouped "opened hub files" cache (`cache/files-audio`, `cache/files-share`, `cache/shared`), which is deleted entirely when any group is disconnected (and on unpairing) (#4990, `clearOpenedHubFiles`); other groups fetch again when they need it.

## Cache size budgets

`cacheBudgets = CacheBudgets(...)` in `HubDataStore` sets separate budgets, in bytes, for items, chat images and Inbox files. The defaults are 32 MiB, 128 MiB and 128 MiB respectively; these are an initial policy, **not measured**, and do not represent actual memory use or an assessment of device capacity.

- Items still keep the last two turns, strip the raw bytes of embedded images, and are charged by the UTF-8 byte count of the JSON in the database. Over budget, whole sessions are evicted by most recent read/write time, and their cursors are deleted too, so no false continuity record is left behind. A session is protected while a page subscribes to it; when protected data alone exceeds the budget, eviction is postponed and cleanup catches up once the last subscription is released. SQLite pages, indexes and the WAL are not counted against the JSON budget, and the database file may keep reusable free pages; this is not a hard cap on the database file's size.
- Chat images are downsampled proportionally to Coil's display size, orientation-corrected, encoded as PNG and written atomically into the pairing scope. The cache key includes the session, image id and target size, so an unsuitable thumbnail is never reused; without an explicit size the current screen size is used. Images are charged by their actual file bytes, reads update the LRU, and all images of a visible session are protected. When a single image or protected files leave no room for a new image, the write is refused and the existing image failure notice reports it.
- Inbox files are charged by the bytes actually written to disk; hits are reused directly, and over budget the least recently used files are evicted. File descriptors the system viewer opens through FileProvider hold a protecting reference, released on close; when a single file exceeds the budget, or open files fill the budget, the download returns an error. Attachments keep their original content; file downloads are not turned into thumbnails.

The budgets don't cover the outbox, drafts or persistent preferences. Inline Lark images keep using the existing in-memory cache of encoded bytes, with no new on-disk copy of originals. Peak image decoding, SQLite physical usage, cold start and scrolling performance are all unmeasured and still need acceptance on a real device.

## Inbox and assistant response memory

Inbox/assistant JSON requests stream into the decoder on `Dispatchers.IO`, without first retaining a complete byte array and string. A process-wide permit covers request through decoding, so simultaneous repositories and pairing scopes cannot accumulate buffered responses while waiting to parse. Waiting callers are cancellable; decoding checks both coroutine cancellation and the current pairing before reading chunks and before returning a result.

The decoder rejects responses exceeding 4 MiB of decompressed JSON, 100,000 structural delimiters outside strings, or 128 nesting levels with `response_too_large`. The structural budget also bounds compact JSON that expands into many small objects. These are safety limits, not truncation or pagination: over-limit results are not partially applied, and existing repository data remains. Large endpoints still need server pagination to return additional data. Existing media and APK streaming behavior, authentication, TLS and pairing data are unchanged. A device crash stack identifies an allocation failure, not necessarily the largest retained object; large-response/concurrency regression tests do not replace device validation of the reported crash.

## Error reports (#5533)

The app's crashes and ANRs go to the hub's `error_reports` (format and rules: [protocol.md](../protocol/protocol.md) "Error reports"). The pure parts are in `:core:hub` (`persona.core.hub.errors`: report builder, disk queue, sender, exit-reason planner, ANR trace parser, breadcrumbs); `app/errors/ErrorReporting.kt` wires them into `PersonaApp`. There is no UI.

- **Crash**: an `UncaughtExceptionHandler`, installed first in `PersonaApp.onCreate`, writes the report synchronously (kind `crash`, level `fatal`, `previous_launch` true) and then hands the crash to the previous handler. It never throws; writing is one small file.
- **Next start**: `getHistoricalProcessExitReasons` turns `REASON_ANR` (kind `anr`, the main thread's Java frames parsed from the trace, nothing else from it) and `REASON_CRASH_NATIVE` into reports, each once (the newest exit timestamp seen is kept in the `error-reports` preferences). `REASON_CRASH` is reported only when the Java handler did not write it (no handler crash time within 10 s before the exit). The first run only records where it is: exits from before the reporter are not sent.
- **Content**: exception types, messages (`message` ≤ 1 KB), frames (class, method, source file name, line; `in_app` for `persona.*`), at most 5 causes × 64 frames, the release (`versionName`), build (`versionCode`), Android version and `Build.MODEL`. Breadcrumbs are the last 20 navigations through `AppNavigator` (route type names and tab names, never route arguments); pages that switch content without the navigator leave no breadcrumb.
- **Queue and sending**: one JSON file a report in `files/error-reports/`, at most 50, at most 7 days old. Sent only to the selected group's hub (the one the hub-level pages show), whenever its connection is online and its hello's `features` has `error_reports`; online without it, the queue is deleted. Batches of ≤ 20 reports and < 240 KB through the connection's authenticated route (same token and `X-Persona-Client`), on `Dispatchers.IO`. 2xx deletes the batch (and `{"enabled": false}` deletes the rest); 4xx drops it, except 408 / 429; 5xx or no answer keeps it for the next time.

## Internationalization (简体中文 / English / 日本語, #2453)

Shared conventions (language list, fallback, glossary, protocol fields) are defined in `docs/protocol/i18n.md`; this section only covers how Android does it.

- **Languages and fallback**: `AppLanguage` (`core/contracts`) has four options: match system, 简体中文, English, 日本語. When matching the system, only the system's first preferred language counts (`docs/protocol/i18n.md`; it doesn't look further down): any Chinese (Traditional included) shows Simplified Chinese, Japanese shows Japanese, and everything else is English.
- **Switching**: Settings › Appearance › Language (`LanguageSettings.kt`). On Android 13 and above it writes the system's per-app language (`LocaleManager`, with the three languages registered in `res/xml/locales_config.xml`), so "App language" in system settings sees and changes the same value; on older systems it's stored in the App's own preferences and the Activity is `recreate()`d after switching. `AppCompatDelegate.setApplicationLocales` isn't used: the App's Activities are `ComponentActivity`, and below 13 AppCompat requires `AppCompatActivity` and an AppCompat theme, which costs more than applying the Configuration ourselves.
- **Applying it to the UI**: every Activity, `HubService` and the Application pin resources to the display language in `attachBaseContext` through `AppLanguages.wrap` (it only overrides the locale; light / dark and sizes still follow the system). This way a Traditional Chinese system also lands on `values-zh` (`zh-TW` would otherwise not match `values-zh` and fall through to English).
- **Resources**: `values/` is the English fallback, Chinese is in `values-zh/`, Japanese in `values-ja/`. English is the fallback because the fallback rule is "every other language shows English": with a French system Android takes `values/` directly; if `values/` were Chinese, French users would see Chinese, and places where the system reads resources directly without the App's Configuration (widgets, tiles, notification channel names) couldn't be fixed. `values-zh` has no region and covers `zh-CN`, `zh-Hans`, `zh-SG`. When packaging the App, `localeFilters` keeps only en / zh / ja, so libraries' bundled French and other translations don't leak into the English UI.
- **Keys**: all modules' resources merge into one table, so keys start with the module name (`settings_…`, `chat_…`), and each module keeps its own `strings.xml`. Language self-names ("简体中文", "English", "日本語") and the name Persona are marked `translatable="false"` and live only in `values/`. Plurals use `plurals` (English needs one / other, Chinese and Japanese only other).
- **Dates and numbers**: `LocalizedFormats` (`core/designsystem`) picks formats by skeleton (which fields to show: `MMMd`, `jmm`…), and the language decides order and wording; pages never write patterns containing words (`M月d日`). Inside Compose use `currentLocale`; outside Composables use `LocalizedFormats.locale(context)`.
- **Text from pure JVM modules**: `core/contracts`, `core/domain` and `core/hub` have no resources, so any human-facing text is returned as `CoreText` (`core/contracts`, a key plus arguments; lists and concatenation use `CoreText.joined`, user names and the hub's verbatim text use `CoreText.plain`), with entries in `res/values*/strings_core.xml` in `core/designsystem` (`designsystem_core_…`). Pages call `text()`, places with a Context call `resolve(context)`; places with no resources at hand (pure notification functions, exception messages, text that `core/data` repositories put into state) use `shown`, which goes through `CoreText.words`, pointed at the App's own resources in `PersonaApp.onCreate` at startup. Failures use `CoreTextException` (its `message` is the text in the current language). Unit tests: Android modules have `values-zh/strings_core.xml` on the test classpath (build-logic), `shown` reads it, and expected Chinese is written as is; JVM modules' tests read the same file through their own `zh()` helper. Demo mode data comes in three copies per language: `Demo.json` (Chinese), `Demo.en.json` and `Demo.ja.json` in `core/demo`, picked by the current language when entering demo mode.
- **Passing it to the hub**: `ClientLanguage` (`core/contracts`) holds the language currently displayed (`zh-Hans` / `en` / `ja`); the hub client sends `Accept-Language` on every request and WebSocket upgrade, and `client_hello` carries `locale`; when the language changes, `client_hello` is sent again on the current connection (`docs/protocol/i18n.md` ("Protocol")). Android doesn't register push devices, so there's no device `locale`.

## Design token adoption baseline

Run the standalone check from the repository root; no Android SDK needed:

```sh
python3 scripts/app/android_token_baseline.py
python3 scripts/app/android_token_baseline.py --report /tmp/android-token-report.json
python3 scripts/app/test_android_token_baseline.py
```

The baseline is stored in `android/core/designsystem/tools/token-baseline.json`. The script scans production Kotlin under `android/feature/*/src/`, skips test directories, ignores comments, strings and imports, and recognizes explicit imports and aliases. It counts hard-coded values, token references and adoption rates per module for colors, font sizes and dp; adoption is `token / (token + hard-coded)`, or `null` when there is no usage.

Colors include numeric `Color(...)`, named constants and `parseColor(...)`; font sizes include numeric `.sp`; dp includes all numeric `.dp`, including spacing, sizes and radii. Tokens include the corresponding `Tokens`, `PersonaTheme.colors`, `PersonaTypography` and theme-mapped `MaterialTheme` references. These are source-reference counts, not runtime style coverage; variable propagation, wildcard member imports, expressions inside string templates and custom wrappers are not fully analyzed semantically.

Since the 2026-10-31 redesign, `PersonaTheme.palette` / `type` / `shapes` also count as tokens; feature colors and font sizes all use tokens, while spacing between page elements still uses numeric dp (each style's internal padding lives in design system components). The baseline was updated once against the redesigned code.

Hard-coded counts for each file and category must not exceed the baseline; new files start at zero. Existing code with permitted fixed sizes, such as the terminal, also counts toward the baseline, and new usage is checked too. Reducing hard-coded values in another file does not offset additions in this file. When a change really must be accepted, run `python3 scripts/app/android_token_baseline.py --update-baseline` and review the baseline diff; the normal check never rewrites it. After merging several lanes, run the check first, fix new hard-coded values first, then decide whether to update the baseline. The Swift output is out of scope here.

## Interface style performance

(`debug.style` switches style, `debug.automation` disables dropped-frame fallback so the measurement captures the cost of glass itself), wait 3.5 seconds, reset `dumpsys gfxinfo`, swipe twice in each direction,
then read framestats. Frame time = `FrameCompleted − IntendedVsync`; each run takes the last roughly 120 frames in framestats (unfinished and invalid rows removed), 10 runs per scenario.
Jank rate is gfxinfo's own "Janky frames ÷ Total frames", summed across 10 runs; parentheses show per-run min / p50 / max.
The chat scenario is the phone's longest Agent session (largest transcript); the first round used the Persona main chat, which rendered only about 20 frames each time (it never started scrolling), so it does not count.

| Agents list | Board | 993 | 2.8 | 7.1 | 10.3 | 32.2 | 8.03 | 1.02% (0.2 / 2.3 / 4.6) |
| Agents list | Glass | 988 | 5.2 | 10.9 | 15.5 | 51.1 | 11.31 | 1.75% (0.3 / 2.3 / 4.4) |

| Inbox | Board | 992 | 2.6 | 7.0 | 10.9 | 43.5 | 8.34 | 1.38% (0.0 / 3.1 / 5.3) |

Conclusion: on list pages glass adds 2–4 ms to median frame time over the other two styles, with a jank rate comparable to Brief. The chat page has the most overlays (top bar, task strip, status line, composer and two scroll edges),
and glass's median frame time is twice the other styles'. Blur input was therefore reduced to quarter resolution (`LocalHazePerformanceMode` = `Performance`, `PersonaTheme`),
with no visible difference in screenshot comparisons. Phone results after lowering resolution: not measured (the phone dropped adb halfway).

Emulator figures are only a reference (emulated GPU, very slow RenderEffect): glass median frame time is 166 ms for Agents and 261 ms for chat, versus about 17 ms for Brief and Board;
at quarter resolution glass is 103 / 126 ms. The fallback below normally takes over on such a machine.

Fallback: when scrolling repeatedly drops frames (over 30% of 240 frames exceed 1.5 times the frame budget), `GlassFrameMonitor` drops one level for this run (refraction → blur → opaque);
battery saver and "Reduce transparency" use opaque panels directly (verified on the emulator by unplugging and enabling battery saver: floating dock and top bar become opaque, scroll edges become gradients). Battery usage: not measured.

Only the last three animate continuously (about 12 frames/second); idle moves only when blinking. With "Reduce motion" or battery saver each state stays on a still frame (like iOS low power mode).
- State derivation (`personaState` in `feature/assistant`, same rules as iOS `AppModel.personaState`): unable to reach the hub (connecting, waiting for network, etc.; "Updating" doesn't count) or this chat's machine offline means offline; a chat waiting for you (`needs_you` or a pending interaction) means needs you; a running turn means working; otherwise idle. It looks at the currently open chat; a new-chat page has no chat, so it only checks whether Persona's machine is online and is otherwise idle.
- Differences from iOS: this page cannot access the chat's last item, so it cannot distinguish thinking from working; any running turn shows working. The needs-you ring uses the Android design system's needs-you color (orange), not iOS red. Mochi keeps its App icon colors in every style. iOS adds a small pale-red dot at the bottom-right of the face when the Inbox has items; Android's Inbox is a separate bottom tab with its own indicator, so the face doesn't carry one.

- Hub avatar packs (`docs/apple/persona.md` ("Pack format"), same rules as iOS `PersonaStore`): `PersonaStore` in `core/designsystem`, one per device, not tied to the hub.

## APK update discovery

The paired app checks its hub's APK feed on launch and when returning to the foreground. Automatic attempts, including failed ones, are limited to one per six hours per hub; Settings › Check for updates bypasses that interval. No resident background timer is required or promised. Demo mode and onboarding do not check automatically.

A nonmodal notice offers Download and install. Closing it remembers that version for that hub; the update remains available in Settings, and a later version can show a new notice. Last-check time and discovered metadata survive process restarts. Switching hubs uses separate state and rejects results or downloads whose source changed. Automatic failures stay quiet; manual checks and download failures provide retry feedback without blocking other app features.

Checks and installation preparation share a nonqueuing gate. Downloading continues if its notice is closed or Settings is left. APKs use the existing authenticated, pinned hub transport and are verified by SHA-256, package name and increasing version code. One verified APK is retained in app cache for retry after cancelled installation; pending installer sessions prevent another download, and abandoned uncommitted sessions are cleaned before retry. Installation always opens the Android system confirmation and may require allowing installs from this app first. Publishing an APK does not install it on a phone.

Regression coverage: `AppUpdateStateTest`, `AppUpdateNoticeShotsTest` (including lifecycle events and all three styles in light/dark), `AppUpdateTransportTest` and `AppInstallerTest`.

## Inbox: background refresh does not move the list (#1947)

- **Refresh**: `RealInboxRepository` refreshes only on `{"type":"inbox"}`; bursts are combined (`refreshWindowMillis`, default 1 second, using `sample`), and an event arriving during refresh triggers another after completion. `{"type":"lark"}` only reloads the currently displayed Lark chat, not the list: the hub emits `inbox` when the list changes, as iOS does. ## Hub links in assistant answers (#2680)

When an http(s) link is tapped in chat, `ChatLinkHost` first asks the shell (`LocalChatHubLinks`, `openHubPage` in `app`'s `ShellLinks.kt`): if host:port belongs to the selected hub group
(pairing address, alternate routes, hub-provided endpoints including `public_url`, other group hubs; `OkHttpHubConnection.knownAddresses`; reverse-proxy subpath prefixes stripped),
and the path matches an App page, navigate directly instead of opening a link card; otherwise open the card as before. Path parsing uses `HubLinks.page` in `core/navigation` (same paths as web `web/src/lib/router.ts`):

| Link | In the App |
| --- | --- |
| `/s/<machine>/<session>`, `/t/<machine>/<space>/<slot>/<session>` | That Agent chat (a short session id is used only if it matches one session); `/t/…` without a session opens Agents |

| `/inbox/<id>`, `/inbox`, `/agents`, `/settings`, `/machines[/<machine>]` | Corresponding page |

Machine ids are the hub's raw ids plus group suffix (`GroupKeys.machine`). Queries and anchors (`?view=`, `#…`) do not affect recognition.

`itemId` in `HubPage.Agent` / `HubPage.Conversation`. The route remains that chat's `ChatRoute` (one stack entry per chat; assistant chats display in place on Persona home).

## Lessons

- Never read response bodies on the main thread: pairing starts requests in a main-thread coroutine; reading body triggers StrictMode `NetworkOnMainThreadException`,
  with only generic Connection failed / Connection incomplete in the UI (`PersonaPairing` logcat has the reason). JVM unit tests miss it; it also depends on whether body arrives with headers:
  `adb reverse` via 127.0.0.1 often arrives in two chunks and fails, while small responses over the emulator's documented host alias sometimes pass by luck.
  `awaitResponse()` now buffers the body on OkHttp's thread by default; only APK downloads use `buffered = false`, streaming on `Dispatchers.IO`.
- Emulator screenshots (both light / dark required, `docs/operations/testing.md` ("UI checklist")):
  - Dedicated AVD, fixed port (`emulator -avd <name> -port 5600`), all adb commands `-s emulator-5600`; leave others alone.
  - Delete the AVD you created when the lane is merged or abandoned (`avdmanager delete avd -n <name>`); each one keeps 2–4 GB of user data on disk.
  - Data from `scripts/mock/mock_hub.py`, deep-link pairing. Device shell truncates URL `&`; wrap the whole command in another quote layer:
    `adb shell "am start -a android.intent.action.VIEW -d 'persona://pair?url=...&token=mock' <package>"`, then tap Connect on confirmation.
  - Before every screenshot `am force-stop`, then cold start; otherwise each tab's stack retains the prior detail. Chat direct entry `persona://open?machine=&session=`.
  - Find text nodes' coordinates with `uiautomator dump`. Duplicate labels (Settings is both bottom tab and Agents gear description) require coordinate taps.
- `adb shell input swipe` downward from the very top opens system Quick Settings; start historical scrolling from screen center.
- A newly created AVD occasionally has no network on first boot (`eth0` DOWN in `ip addr`, no NetworkAgent in `dumpsys connectivity`); App stays on "Showing local cache" after pairing. Restart emulator once.
- A key input (TAB, BACK, `input text`) leaves touch mode; later cold starts focus the first focusable control (phone Agents top-bar New session, extra focus outline in screenshots). Before cold start, the screenshot script taps the launcher's status bar to return to touch mode.
- `HubService` starts with `startForegroundService`. Stopping it before `startForeground` (`stopSelf` or external `stopService`) crashes with `ForegroundServiceDidNotStartInTimeException` (logcat first: "Bringing down service while still waiting for start foreground"). This caused frequent pairing crashes on heavily loaded screenshot machines (confirmed 2026-11-02). Three former paths: `onStartCommand` immediately `stopSelf` if unpaired/user stopped; `NotificationRuntime` `stopService` on `isPaired` changing true/false before our start foregrounded; system start (new-process service restart, `am start-foreground-service`) stopped in `Application.onCreate` before foregrounding. Now service always enters foreground before deciding, uses `stopSelf(startId)` to avoid stopping newer starts; `HubService.stop()` calls `stopService` only if already foreground, records pending stop for our starts not yet foreground (`ForegroundStarts`), otherwise leaves the service to decide. Repro: after emulator `adb root`, run `am start-foreground-service -n <package>/persona.platform.notify.HubService` with an unpaired App; always crashed before, now foregrounds then stops itself.
- herdr server inherits its launching shell environment: starting it with proxy variables also routes claude through that proxy. Use a clean login shell for integration tests.
- Tools allowed by Claude Code allow rules/bypass do not trigger PermissionRequest; test permission cards in a session without those allowances.
- `JsonCodec` `encodeDefaults = false` omits default-valued fields, while hub treats missing as empty/false: scheduled task `enabled = true`,
  `time = "09:00"` were omitted and saves disabled tasks or returned 400. Fields sent to a hub that treats omission as empty need `@EncodeDefault`, or a hand-built body like scheduled tasks (`ScheduledTask.editable()`, `AssistantManagementTest` checks exact requests).
- OkHttp does not retry WebSocket upgrades on a dead connection: after forwarding (adb reverse, ssh -L) breaks once, reconnects return `unexpected end of stream` until App restart.
  Evict connection pool on WebSocket failure (`connectionPool.evictAll()`).
- Inverted chat lists (`reverseLayout`) preserve first-visible position on insertion at the front: growing/new replies leave even latest-position readers stationary. Explicitly scroll to 0 when already at latest or just sent a message.

Tested emulator/Robolectric: removing `clip`, or keeping layer (`graphicsLayer { alpha = … }`, or 0.999) fixes it; removing `clickable` doesn't; press `scale` layer at chain start is unaffected. Thus that test passes old code as well; it only guards restored appearance.

### Lessons from the old main-line App

Imported when merging main line 2026-11-02: pitfalls from the old single-module App; class/file names here refer to that App (original text via `git show origin/master:docs/android/android.md`, code in pre-merge main-line history). Use as reference when implementing similar features in the new architecture.

- Folding changes `screenSize` / `smallestScreenSize`; without `configChanges`, Activity rebuilds. Compose `rememberSaveable` restores,
  Activity fields (`MainActivity.openSession`, notification-opened chat) do not, so folding closes chat; recreation also reprocesses launch intent,
  reopening a notification chat the user closed. Now declares `configChanges`, saves open chat in `onSaveInstanceState`, handles launch intent only on first `onCreate`.
- Custom panels (two-pane right side, placeholders, Persona left side) need `Surface(color = …)`, not `Modifier.background`: only Surface sets `LocalContentColor`;
  default `Text` is black, making dark-mode titles/body invisible on black (old bottom sheets/Scaffold had Surface, so single-pane unaffected).
- Same page at different Compose-tree positions across layouts loses position-based `rememberSaveable` (drafts, viewed Persona chat): wrap each with `SaveableStateHolder.SaveableStateProvider(key)`;
  `removeState` for pages no longer drawn, or closing/reopening returns to old scroll position instead of latest.
- Don't put full-screen images in Compose `Dialog`: window stays between status/navigation bars (tried `decorFitsSystemWindows = false`, `FLAG_LAYOUT_NO_LIMITS`, underlying page still visible at edges).
  Draw over chat directly (`ImageViewerOverlay`), set status icons light while open, restore on close.
- `Markdown` defaults to `SelectionContainer`; long press opens system text selection instead of message menu. Chat replies use `selectable = false`; menu Select starts selection.
- Inverted list `verticalArrangement = spacedBy(x)` packs at top with few messages; use `spacedBy(x, Alignment.Bottom)`.
- Chat verification uses `scripts/mock/mock_hub.py`: `MOCK_CHAT_IMAGES=1` adds two screenshots to "博客迁移" ("Blog migration") for viewer/editor; files/Git use fabricated `~/code/weather`.
- Xiaomi / HyperOS `adb shell input` requires Developer options › USB debugging (Security settings), then `adb reconnect` to apply;
  occasional consecutive `SecurityException: Injecting input events requires … INJECT_EVENTS` recover after seconds; test clicks wait 3 seconds and retry on denial.
- Terminal typing: Android IMEs compose even English words for suggestions; waiting for commit delays a word until space. Send only each change's delta, including composing text
  (new characters or backspaces). Pinyin appears first, then backspaces replace it with Chinese on selection (emulator has no Chinese IME, not device-tested yet). Android emoji fonts render ⏺ ⏸ ⏵ as two-cell colored icons;
  U+FE0E does not help, so draw these shapes ourselves.
- After forwarding breaks, hub may still consider node online but every call returns `rpc: connection closed` (including /screen). Restart persistent node
  (`launchctl kickstart -k gui/$UID/com.persona.node`), reconnect machine from hub; no App change.
- `adb shell am start` with an intent identical to current task root only foregrounds it ("Activity not started"), no onNewIntent;
  verify shortcuts through launcher long-press, or leave App on another page first.
- Application-context WebView always stays light: application context lacks App theme (`isLightTheme` true); WebView only supplies
  `prefers-color-scheme: dark` / algorithmic darkening when outer theme is dark. Pool WebViews use `ContextThemeWrapper(app, Theme.Persona)`; `values-night` `Theme.Persona` is dark with `isLightTheme=false`.
- Adding WebView selection actions: Chromium fills menu in `onPrepareActionMode` on every selection change, all its items demand button display, which floating toolbar prioritizes;
  custom items also need `SHOW_AS_ACTION_ALWAYS` and lower order to precede Copy. Read selection with `evaluateJavascript` before `mode.finish()`; finishing first clears it and returns empty.
- `scripts/mock/mock_hub.py` with `MOCK_RICH=1 MOCK_LINKS=1` adds links to chat, Persona main chat and Inbox.
- Paparazzi renders one frame: synchronous state changes in `LaunchedEffect` appear, network/delay-dependent ones don't. Pages must preload data: hub status in `Hub`
  StateFlow (test `refresh()` first), chat in `hub.chat(key)` (wait `loading = false`), assistant in `AssistantModel` (test `reload()` before `ShellRoot`).
  Leaving chat calls `hub.release(key)`; preload again before second dark shot. Page network responses may arrive before screenshot and overwrite injected data:
  injected data must match mock results. Paparazzi reports retain old runs; delete before copying by name (`android.sh shots` does).
- Paparazzi/layoutlib WebView is a stub: class exists, `getSettings()` doesn't, causing `NoSuchMethodError`; no `LocalInspectionMode` / `isInEditMode` either.
  Screenshot WebViews (mail) reflectively check for `getSettings`; otherwise draw substitute (`MailWebView` uses `MailHtml.toText`).
- No Activity in Paparazzi: `rememberLauncherForActivityResult` needs `LocalActivityResultRegistryOwner`, `BackHandler` needs `LocalOnBackPressedDispatcherOwner`,
  faked by `ShotHost`; no `PersonaApp.instance` (composition reads need `runCatching`); services like `PowerManager.isIgnoringBatteryOptimizations` throw `Unsupported Service`.
- Persistent two-page shell: top page root needs `pointerInput`, or blank-area touches fall through; hidden page uses `clearAndSetSemantics` to hide from accessibility.
  Later children in Box are above earlier ones unless `zIndex` changes it; page `zIndex(1)` requires top bar `zIndex(2)` or hides it (the initial bug).
- Two weights divide remaining width: title `weight(1f, fill = false)` plus `Spacer(Modifier.weight(1f))` limits title to half and truncates on short screens.
  Put title and adjacent small elements in one `weight(1f)` Row, time outside.
- Chinese lines are taller (Noto CJK line spacing); same-size bullet "•" floats above Chinese. Both marker/text use `alignByBaseline()`.
- `WindowInsets.statusBars.asPaddingValues()` returns raw values regardless of outer consumption: pages computing top padding (`AgentsScreen`, shell chat)
  must be in a pane starting at window top; `statusBarsPadding()` pages (`PageHeader`, chat top bar) go in a pane offset only by shell bar height, adding status-bar space themselves.
- Moving pages in composition (single ↔ two panes) loses `remember` / `rememberSaveable`; cross-layout state like drafts belongs outside the page.

- Hub stores one phone_* list (`setPhoneTools`), replaced by every `register_phone`; calls go to last registered `phoneClient`.
  Android tools must exactly match iOS, no extras or parameter changes. Since Android 10 only foreground Apps can read clipboard; background `phone_clipboard_get` gets empty and explains in result.
- With two connected phones, phone_* goes to last registered: close Persona on physical phone when testing emulator tools, or calls reach that phone and time out if its data source is off.
  Claude Code reads tool list only on startup; newly added tools need a new session.
- Emulator has no writable calendar account by default; `phone_calendar_create_event` says "no writable calendar". Create a LOCAL calendar with `content insert` for tests.
- Opening a pairing link while paired: clear `pendingPair` only after pairing completes. Earlier clearing makes Root switch back immediately, disposes pairing page/coroutine, and loses the link.
- Headless (`-no-window`) emulator `adb exec-out screencap` sometimes returns previous frame: immediate shot looks unresponsive although navigation occurred. Capture twice, one second apart.
- Read-only real-hub UI inspection: pairing adds a device with `POST /api/v1/auth/tokens`. Debug can `run-as` write `shared_prefs/pairing.xml` (`url`, `token`) directly, launch, then `pm clear`; don't tap hub-writing switches (Claude Code settings, notifications, phone data).
- Byte-based chart y-axis rounds in 1024 (`ChartMath.yTicks(binary = true)`); decimal rounding shows "1.91 MB/s", "3.81 MB/s". Measure label width from widest label; fixed width clips.
- Mock hub (`scripts/mock/mock_hub.py`) does not push pending interactions on WS connect; pull to refresh once after opening.
- Lark screenshots (`LarkShots`) need `MOCK_LARK=1` (message types, emoji library, images). Images decode in background and miss first frame. Capture once with same name to trigger loads, wait `LarkMedia.settle()` (no downloads), then actual shot; nested-image link previews may need 2–3 cycles. Default mock f2/f3 are separate data (iOS screenshots, TranslationTests, fully rendered f3); `MOCK_LARK=1` replaces these chats with this fixture; sets do not affect each other.
- Inbox details use `JSheet` (ModalBottomSheet, separate window), above link cards/image viewer. Chats needing links/images should be pushed pages over list, not sheets; profile/topic/Moments sheets close themselves before opening links/images (`LarkActions.closing`).

## Cross-app floating capsule (#2124)

Settings › Floating capsule defaults off, Show with tasks / Always show; first enable grants system Display over other Apps.
Native TYPE_APPLICATION_OVERLAY, independent of status-bar Live Updates, supported on project Android12+.

- Collapsed 56×36 dp: the avatar centered, the unread dot on its top-end corner; drag snaps to the nearest edge and remembers the relative height. Expanding grows the card out of the capsule and fades it in (the V7 design's ease-out); collapsing pops the capsule back; reduced motion skips both.
- One tap opens the current conversation ready to type: the app's current conversation first, else the newest unread, else the main chat. The bar has the conversation title (opens the unread list), **Next** (a tinted pill), **Expand**, **More** and a collapse button; tapping outside also collapses. **More › Close capsule** turns the capsule off (Settings › Floating capsule turns it back on).
- Unread is a list grouped like the Agents page: one herdr workspace per computer, else the session's repository, and Feishu conversations in one **Feishu messages** group; each group has **Mark all read**. The main chat is the other section. Inbox documents, moments and doc comments have no read receipt here and stay in the app's inbox.
- Agent and Persona replies render as Markdown without a bubble; people's messages and your own stay bubbles. A reply on screen for about 0.75 s marks the conversation read through the app's read path (Agents: seen versions; Feishu: the conversation's read position, sent as a string as the extension expects); the dots go at once and return if the receipt fails. **Next** marks the current conversation read and moves on, even before a Feishu window has loaded.
- Conversations read or passed with Next are remembered with their newest message and stay out of the list, the badge and Next until a newer message arrives (Feishu counts move between the hub's inbox record and Feishu, so they are no signal); the record survives restarts and updates. Mark all read for Feishu acknowledges each conversation's newest page directly, four at a time; a topic group whose thread replies Feishu still counts stays read here.
- New completion temporarily shows one line session · Completed (or · New message), about 4 s, then the small capsule; queued sequentially, tap opens the target. A separate non-focus notice: no transcript, no IME, no change to the manual choice or draft.
- Tracks the turn observed Working while online, including completion after a NeedsYou wait; first fresh snapshot after reconnect is only a baseline, never guesses unseen runs. Independent of system long-task notification filters.
- Independent session drafts through the existing persistent outbox / group routing. Transcripts are observed only while expanded.
- Stay on screen: an optional accessibility service (`CapsuleKeeperService`, Settings › Floating capsule › Stay on screen) that reads no window content and handles no events. The system binds it and rebinds it after the process dies, which an overlay alone does not survive on phones that clear background apps on lock; on connect and each unlock it asks for the resident connection. A force-stop turns any accessibility service off; some systems also turn it off when the app updates itself, so after an update (and on start) the app turns it back on when `WRITE_SECURE_SETTINGS` was granted once over adb, or posts a notification that opens the accessibility settings.
- Performance with the process resident: session events write the first-paint snapshot at most every 10 s; the capsule catalog and inbox rows rebuild from the latest inputs only; at most three unread Feishu windows are prefetched and only four idle windows stay in memory. With any accessibility service on, Compose diffs the semantics tree on every recomposition, so the Agents page redraws at most every 300 ms.
